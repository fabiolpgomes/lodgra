# Story 31.7: Multi-Tenant Launch Hardening

## Status

Ready for Review — Option B foundation

## Goal

Establish the Phase 0–2 deny-by-default organization, onboarding, critical RLS,
and privileged-route foundation required before Lodgra sells subscriptions.

## Acceptance Criteria

- [x] The product owner approves the phased hardening strategy and ADR.
- [x] New signup atomically creates one organization and its first admin.
- [x] Legacy orphan repair is authenticated, idempotent, and tenant-safe.
- [x] Runtime code contains no fallback to the legacy Default organization UUID.
- [x] The Premium plan supports the existing property portfolio without limits.
- [x] Every RLS-enabled table with `organization_id` has at least one policy.
- [x] Anonymous users cannot execute a public `SECURITY DEFINER` function.
- [x] Lint, typecheck, unit/integration tests, and production build pass.

## Evidence

- Production organization for `fabiolpgomes@gmail.com` is Premium, active, and
  currently owns 11 properties.
- The new Portimão property was created successfully at 2026-08-14 19:42 UTC.
- Atomic onboarding and critical RLS migrations were applied to production.
- Production audit returns zero tenant tables with RLS and no policy, and zero
  `SECURITY DEFINER` functions executable by `anon`.
- `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build` pass.
- Full Jest result: 214 suites, 2811 passed, 1 skipped.

## Remaining Launch Blockers

- The new property has no Booking/iCal listing yet and therefore has zero
  imported reservations; connection configuration is required.
- Non-tenant internal tables still reported by Supabase advisors require an
  explicit internal-only policy or schema relocation.
- Cross-tenant negative tests and service-role classification remain mandatory
  before paid launch.
- Backup/restore, rollback, integration, and observability gates remain pending
  in the approved phased launch-hardening plan.
